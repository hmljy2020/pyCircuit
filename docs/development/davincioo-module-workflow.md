# DavinciOO 单模块开发工作流

本流程记录 2026-09-09 确认的当前开发范围，适用于 Decision 0222 允许的
`designs/davincioo/` 设计工作。框架语义和验证要求仍遵循
[设计工程约定](davincioo-design-program.md)与[测试和门禁](testing-and-gates.md)。

## 当前目标与验收范围

逐模块表达并验证正确功能，同时在设计文档中考虑模块之间的影响关系。
当前不要求把所有模块连接起来证明整体正确；完整连接、跨模块时序与系统级
正确性留到集成阶段验收。

模块间的依赖必须写清楚：谁提供输入、谁接收输出、谁拥有状态、谁负责取消、
释放和恢复，以及本模块依赖外部保证什么。测试可以模拟这些外部行为，
但不能因此宣称真实的上下游模块已经履行了约定。

每个模块的规则 NDF、实现代码和测试一起推进。NDF 是实现和验收的依据，
不是代码完成后的补写说明。只讨论影响实现的重大决定，常规细节按现有契约处理。

## 1. 确定模块责任和影响关系

先阅读模块卡、相关模块卡、共享类型及适用的框架决议，确认该名称是独立模块、
内部状态还是别名，避免重复创建状态所有者。

在模块设计 Markdown 中记录：

- 输入、输出的类型、身份字段和实际含义。
- 本模块拥有的状态、容量、初始化及复位行为。
- 上下游关系和外部假设，包括背压、重复消息、取消和恢复责任。
- 本次实现范围、已有决定和真正影响实现的未决问题。

涉及其他模块的约定，也在相关设计文档中注明或链接。尚未由对方确认的假设
保持待确认状态，不写成已实现事实；这不阻止在明确假设下进行单模块开发和测试。

## 2. 划分 rule，编写规则 NDF

按状态转移划分规则，例如分配、完成、交接、确认释放和恢复。
为每条规则计划并编写较准确的 NDF 描述，至少覆盖：

| 内容 | 需要回答的问题 |
| --- | --- |
| 边界与资格 | 消费什么输入？什么条件下可以执行？如何检查身份和 generation/epoch？ |
| 状态变化 | 读取哪些提交前状态？修改哪些字段或槽位？ |
| 输出 | 何时输出什么？输出表示受理、完成还是释放授权？ |
| 原子性 | 哪些输入消费、状态更新和输出必须全部发生或全部不发生？ |
| 阻塞与拒绝 | 容量不足或输出背压时如何保持状态？非法、过期、重复输入是消费还是保留？ |
| 冲突与恢复 | 与其他规则如何竞争？取消、flush、复位对未完成事务有何影响？ |
| 验证 | 哪些场景和独立预期结果能证明上述行为？ |

一次 `ac.rule` 的本地原子性，不自动提供跨模块、跨多次消息的撤销协议。
需要等待确认、重试或退还资源的行为，应明确写出保留状态和后续规则。
不把一次 gfsim `step()` 直接当作一个硬件周期。

规则文件沿用现有目录形式，例如
`designs/davincioo/spe/ooo/ndf/rob/allocate.md`。可参考
[ROB allocate 草案](../../designs/davincioo/spe/ooo/ndf/rob/allocate.md)。
规则条款使用稳定身份，未评审内容保留 draft 状态；未经核实，不虚构 L0/L1
精化关系或项目登记。规则文档完成与项目级 NDF 检查通过分别记录。

## 3. 同步实现 NDF 与代码

按规则实现模块，使用共享的类型定义，并保持状态归属清楚。
同一行为变更应在同一项工作中同步修改规则 NDF、代码和相关测试；若影响接口，
同步更新模块卡及受影响模块的文档。

Python 实现中，每条 `@ac.rule` 必须用紧邻的注释标记对应 NDF 文件的 `doc_id`。
注释只写代号，不附加路径。例如：

```python
# NDF: DOC-DAV-SPE-OOO-CMT-ACCEPT
@ac.rule
def accept(request, core_id, pe_id, stid, launch_generation):
    ...
```

当 Python 功能逻辑经对应场景测试确认正确后，在该规则的 NDF 文件中加入
“Python 实现示例”，摘录已验证实现中表达该规则功能的代码，并链接实现文件及验证证据。
示例应保留理解条件、状态更新和原子提交所需的上下文；省略部分应明确标注。
后续修改实现时同步更新示例，使 NDF 描述、示例代码与实际实现保持一致。

实现中发现描述遗漏或无法表达时，先明确原因，再修订描述和代码。
涉及已确认语义的重大改变，应先讨论并更新决定；不通过代码悄悄改变契约。

## 4. 遇到框架问题时单独处理

不要把模块卡上的“所需能力”直接视为框架缺陷。先在当前版本尝试表达，
将实际失败缩减为通用的最小复现，区分设计问题、环境问题和框架问题。

确认框架缺陷后，标明受影响的 decision ID，按门禁要求补充通用回归并修复。
语义修复遵循 dialect、pass 和 verifier 的约束，不能只在一个后端打补丁。
共享修复先于依赖它的设计变更合入，然后继续模块工作。

## 5. 单模块仿真和回放

通过 `$pyc6` 的固定环境，从当前 checkout 生成并编译 gfsim 模型。
测试放在 `designs/davincioo/tests/` 对应目录，由测试端模拟外部模块。

按本模块职责选择有意义的场景：正常处理、容量耗尽与复用、输出背压、
错误身份、重复及过期消息、规则冲突、取消与恢复、独立 flow/实例隔离。
预期结果依据契约独立构造，编译成功不能代替功能验证。

生成测试回放动画；发现回放问题先记录复现路径和现象，最后集中修复并复验。
回放只辅助观察，不能代替自动结果断言。适用时检查录制开关不改变仿真行为，
以及不同调度模式的状态与提交结果一致。

当前交付以单模块 gfsim 为目标。PYC/RTL 和完整集成状态单独记录，
不因 Table 等尚未允许的 lowering 边界阻止本范围开发；框架改动仍须运行其必要门禁。

## 6. 记录证据并验收

在 `docs/gates/logs/<run-id>/` 保留可审查的命令、结果、相关决议、
规则/测试对应关系及未解决问题。生成模型、轨迹和动画放在 `.pycircuit_out/`
等输出目录，文档链接到对应产物，避免归档大量生成日志。

单模块验收应确认：

- 模块卡已说明职责、影响关系和外部假设。
- 已实现规则均有注释标记对应 NDF 文件代号，描述、代码和测试一致。
- 功能验证通过的规则，其 NDF 已包含对应 Python 实现示例及实现、验证证据链接。
- 单模块 gfsim 通过适用场景，回放已检查，已知问题有明确结论。
- 本模块已证明的行为、依赖的外部假设和留待集成验证的事项分别列明。
- 交付包含必要源码、文档和测试，其他人能够从交付版本复现。

完成状态使用“单模块实现完成 / gfsim 已验证”等准确表述。
H2/H1 集成、上层 NDF 对应关系和 RTL 验收继续分别跟踪，
不作为本轮单模块功能完成的隐含前置条件。
